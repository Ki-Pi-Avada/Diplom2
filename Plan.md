# Plan.md — План тестирования мобильного приложения «Мобильный хоспис»

## 1. Цель тестирования

Цель тестирования — проверить функциональность и стабильность актуальной версии мобильного приложения «Мобильный хоспис», подготовить набор ручных проверок и определить сценарии, которые будут автоматизированы.

В рамках работы необходимо:
- определить границы актуальной версии приложения;
- проверить авторизацию и выход из учётной записи;
- проверить главный экран и навигацию;
- проверить раздел News;
- проверить фильтрацию и сортировку новостей;
- проверить панель управления новостями;
- проверить создание, редактирование, удаление и изменение статуса новости;
- проверить тематические цитаты;
- выполнить негативные и нефункциональные проверки;
- автоматизировать согласованный набор тест-кейсов с использованием Espresso.

## 2. Границы приложения

### 2.1 Авторизация

Проверяется:
- открытие формы авторизации;
- авторизация зарегистрированного пользователя;
- авторизация с неверными данными;
- авторизация при пустом Login;
- авторизация при пустом Password;
- авторизация при пустых Login и Password;
- отображение сообщения об ошибке;
- повторная попытка авторизации после ошибки;
- выход из учётной записи.

### 2.2 Main

Проверяется:
- отображение главного экрана;
- наличие верхней панели;
- наличие бокового меню;
- наличие кнопки перехода к тематическим цитатам;
- отображение блока News;
- переход в News из блока ALL NEWS;
- открытие и закрытие бокового меню;
- переход между доступными разделами без аварийного завершения приложения.

### 2.3 News

Проверяется:
- отображение списка новостей;
- отображение карточек новостей;
- раскрытие и сворачивание карточки новости;
- отображение заголовка, даты и содержимого новости;
- сортировка новостей;
- фильтрация по категории;
- фильтрация по дате публикации;
- сброс фильтров;
- фильтрация без выбранной категории;
- обработка диапазона дат без результатов;
- обработка некорректного диапазона дат.

### 2.4 Панель управления новостями

Проверяется:
- открытие панели управления;
- отображение списка новостей;
- сортировка;
- фильтрация по статусу «Активна»;
- фильтрация по статусу «Не активна»;
- сброс фильтра;
- просмотр новости;
- создание новости;
- проверка обязательных полей при создании;
- редактирование новости;
- удаление новости;
- отмена удаления;
- изменение статуса новости;
- сохранение результатов операций.

### 2.5 Тематические цитаты

Раздел открывается нажатием на кнопку с изображением бабочки/листа в верхней панели.

Проверяется:
- открытие раздела;
- отображение заголовка;
- отображение списка цитат;
- наличие карточек цитат;
- раскрытие цитаты;
- сворачивание цитаты;
- отображение длинного текста;
- прокрутка списка цитат;
- возврат к основному экрану.

### 2.6 Что не входит в границы

Не планируется:
- нагрузочное тестирование backend;
- полноценное тестирование безопасности API;
- проверка производительности сервера;
- тестирование всех существующих моделей Android;
- тестирование функциональности, отсутствующей в актуальной сборке.

## 3. Виды тестирования

### Функциональное
Проверка соответствия реализованных функций ожидаемому поведению.

### UI-тестирование
Проверка отображения экранов, кнопок, полей, карточек, сообщений и переходов между экранами.

### Позитивное
Проверка корректных пользовательских сценариев с валидными данными.

### Негативное
Проверка поведения приложения при пустых, неверных или неполных данных.

### Smoke
Проверка запуска приложения, авторизации, открытия Main и News, а также выхода из учётной записи.

### Регрессионное
Повторная проверка ранее работавшего функционала после изменений.

### Нефункциональное
Проверка прокрутки, корректности отображения интерфейса, отсутствия наложения элементов и аварийного завершения приложения при основных действиях.

## 4. Инструменты

| Инструмент | Назначение | Почему выбран |
|---|---|---|
| Android Studio | Сборка, запуск и анализ Android-приложения | Основная среда для Android-проектов |
| Android Emulator | Запуск приложения и UI-тестов | Позволяет воспроизводимо выполнять проверки |
| Espresso | Автоматизация UI-тестов | Рекомендован для проекта, подробно изучался в курсе и хорошо интегрируется с AndroidX Test |
| JUnit | Организация и запуск автотестов | Стандартный инструмент для тестового фреймворка Android |
| Allure | Отчётность по автоматизированным тестам | Удобно отображает результаты, шаги и вложения |
| Git | Контроль версий | Позволяет отслеживать изменения |
| GitHub | Хранение и предоставление проекта | Используется для сдачи дипломного проекта |

## 5. Тестовое окружение

Основное тестирование выполняется на Android Emulator, на котором установлена актуальная версия приложения, предоставленная руководителем.

Для каждого запуска автоматизированных тестов фиксируются:
- модель AVD;
- версия Android / API;
- версия приложения;
- версия Android Studio и используемых зависимостей при необходимости.

При наличии возможности дополнительно выполняется проверка на физическом Android-устройстве.

## 6. План автоматизации

Автоматизация строится на тест-кейсах из `Cases.xlsx`. ID в этом плане должны совпадать с ID тест-кейсов.

### Высокий приоритет

Планируется автоматизировать:
- TC-01 — успешная авторизация;
- TC-02 — авторизация с пустым Login;
- TC-03 — авторизация с пустым Password;
- TC-04 — авторизация незарегистрированного пользователя;
- TC-05 — выход из учётной записи;
- TC-06 — переход в News через меню;
- TC-08 — переход в News через ALL NEWS;
- TC-09 — сортировка новостей;
- TC-18 — фильтрация без выбранной категории;
- TC-19 — сброс фильтра;
- TC-21 — просмотр новости в панели управления;
- TC-22 — удаление новости;
- TC-23 — редактирование новости;
- TC-24 — изменение статуса новости;
- TC-27 — создание новости;
- TC-28 — создание новости без категории;
- TC-29 — создание новости без даты публикации;
- TC-31 — создание новости без описания;
- TC-32 — создание новости без заголовка.

### Средний и низкий приоритет

После основных сценариев планируется автоматизировать:
- TC-07 — открытие тематических цитат;
- TC-10–TC-17 — фильтрация по категориям;
- TC-20 — сортировка в панели управления;
- TC-25–TC-26 — фильтрация по статусу;
- TC-30 — создание новости без времени.

Автоматизация может быть расширена после оценки стабильности тестовых данных и UI.

Если запланированный тест-кейс не удастся автоматизировать, причина будет зафиксирована в `Result.md`.

## 7. Приоритеты

Приоритет определяется по:
- критичности функции для пользователя;
- частоте использования;
- влиянию ошибки на дальнейшую работу;
- возможности повторного выполнения сценария;
- риску для основной бизнес-функции.

High — критичные сценарии авторизации, навигации и управления новостями.
Medium — важные, но не блокирующие сценарии фильтрации, сортировки и цитат.
Low — менее критичные повторяющиеся проверки отдельных категорий.

## 8. Оценка трудозатрат

| Этап                                     |      Оценка |
|------------------------------------------|------------:|
| Анализ актуальной версии                 |       1–2 ч |
| Актуализация чек-листа                   |       2–3 ч |
| Актуализация тест-кейсов                 |       1–2 ч |
| Ручное тестирование                      |       2–3 ч |
| Настройка UI-тестов                      |       2–4 ч |
| Разработка автотестов                    |      8–16 ч |
| Настройка Allure и отчётности            |       1–2 ч |
| Анализ результатов и стабилизация тестов |       2–4 ч |
| Подготовка Result.md                     |       2–4 ч |
| **Итого**                                | **21–40 ч** |

Оценка интервальная и учитывает риски, связанные с изменением UI, нестабильностью тестовых данных, проблемами эмулятора и необходимостью стабилизации UI-тестов.

## 9. Риски

Основные риски:
- изменение интерфейса актуальной версии;
- нестабильность тестовых данных;
- изменение состояния новостей между запусками;
- проблемы авторизации;
- нестабильность эмулятора;
- изменение идентификаторов UI-элементов;
- нестабильность отдельных UI-тестов;
- невозможность автоматизировать сценарий из-за особенностей реализации.

При возникновении риска и невозможности автоматизации запланированного тест-кейса причина будет указана в `Result.md`.

## 10. Критерии завершения

Тестирование считается завершённым, когда:
- выполнен актуальный чек-лист;
- тест-кейсы из `Cases.xlsx` выполнены или имеют зафиксированный статус;
- все запланированные к автоматизации сценарии автоматизированы либо для них указана причина;
- автотесты запускаются;
- сформирован Allure-отчёт;
- результаты отражены в `Result.md`.
